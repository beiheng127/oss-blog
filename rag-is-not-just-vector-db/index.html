RAG 不是把文档塞进向量库

链路有六段，向量化只是其中一段。大多数效果问题，出在前面两步。

李亚恒

07 9月 2026 • 阅读时间 4 分钟
分享
Agent AI

一条被讲得太简单的链路

教程里的 RAG 通常长这样：文档切块 → 向量化 → 存向量库 → 提问时检索 → 拼进 prompt → 生成答案。

六步，看起来很清楚。但真做下来你会发现，决定效果好坏的主要是前两步和后两步，中间的向量化反而是最不容易出问题的。

第一关：文档解析

如果你的语料是 Markdown，恭喜你，难度是入门级。如果是 PDF、Word、扫描件、带表格的财报，难度直接跳到地狱级。

PDF 尤其麻烦。它本质上是排版指令，不是结构化文档。双栏论文直接提取会得到左右栏文字交错的结果；表格提取出来经常是一堆数字挤在一起，行列关系全丢。

我的经验是：解析质量决定 RAG 的上限。解析出来的文本本身就是乱的，后面再怎么优化检索都救不回来。宁可在这个阶段多花时间，也不要急着往下走。

第二关：分块

按固定字符数切是最省事的，也是最粗糙的。它的典型失败场景：一个完整的步骤列表被切成两半，检索到后半段时，缺少前置条件，模型读到的信息是残缺的。

改进方向有几个：

  • 按结构切：标题、段落、列表项作为优先切分点
  • 保留重叠：相邻块之间留 10%—20% 的重叠，缓解切断问题
  • 带上下文的块：给每个块加一句它所属章节的标题作为前缀，这样即使单独被检索出来也不至于失去上下文
  • 语义切分：按嵌入相似度找语义边界，成本更高但质量更好

我目前用的是"按结构切 + 章节标题前缀"，性价比最高。

第三关：召回，不要只靠向量

这一段是很多人的盲区。纯向量检索有两个天然弱点：

  • 专有名词：型号、函数名、人名这类词，语义相似度区分度很低
  • 精确匹配：用户搜错误码、版本号，向量检索常常给出"意思差不多"但完全不对的结果

所以实用方案几乎都是混合检索：向量一路 + 关键词（BM25 那类）一路，两路结果合并去重。这一步的收益，通常比换更好的 embedding 模型还大。

第四关：重排（Rerank）

混合检索拿回来的候选可能有几十条，直接全塞进 prompt 会稀释注意力，也会撑爆上下文。

重排模型干的事是：对这几十条候选做一次精细打分，只留最相关的三五条。它比向量检索慢，但准得多，所以放在检索之后、生成之前，是小成本高收益的一环。

顺带一个经验：不要把检索到的内容放在 prompt 的最前面或者最后面。中间位置的信息被模型忽略的概率更高，把关键片段放在开头或者结尾，效果会稳一些。

第五关：引用与溯源

每一段被使用的原文，都要记录它的来源文档、页码/段落、原文文本。前端渲染成可点击的角标。

这件事有双重价值：一是建立用户信任，二是出问题时你能定位是哪一段喂错了。没有引用记录的 RAG，排查问题只能靠猜。

第六关：评估

最容易被跳过，也最不该跳过的环节。

没有评估集的 RAG 优化是这样的：你改了分块策略，跑了几个自己熟悉的 query，感觉好了，上线。一周后有用户反馈答错了，你不知道是检索错了还是生成错了。

最小可行的评估集长这样：

  • 30—50 条真实问题
  • 每条标注期望命中的文档片段
  • 三个指标：召回率（正确的片段有没有被检索到）、准确率（检索到的片段里正确的占比）、答案正确率

前两个指标可以自动化计算，第三个前期靠人工看。数量不用多，30 条就足以看出改动是变好还是变坏。

一个反直觉的结论

大多数"RAG 效果不好"的案例，问题不在模型，而在数据——文档解析烂、分块切断语义、没有引用记录、没有评估集。

换句话说，RAG 八成是数据工程，两成是模型工程。把它当模型问题来解决，方向从一开始就错了。

项目经历真正的考察点

大部分人的简历项目栏写的是功能列表：用户模块、权限模块、文件上传、数据统计。这些内容面试官扫一眼就过去了，因为换个谁都能写。

他真正想听的是另外三件事：

  1. 你在哪里卡住了
  2. 你试过什么，为什么放弃
  3. 最后是怎么解决的，代价是什么

功能列表只能证明你做过，卡点才能证明你想过。

用我自己的项目举个例

我的简历里放了三个项目，每个我都准备了一个"卡点故事"。

hr_recruit（Spring Boot + Vue 的招聘管理系统）

功能层面写：19 张表的领域建模、MyBatis-Plus 的多表查询、JWT 鉴权、简历状态流转。

但如果只讲这些，顶多算"会用框架"。我准备的故事是：简历状态变更接口调不通，前端传的是 JSON body，后端用 @RequestParam 接，参数一直是 null。这种 bug 看日志是看不出来的，只能从网络面板一层层往回推。

第二个坑更隐蔽：Dashboard 统计接口偶发 500，查出来是 Map 里塞了 null key，序列化的时候直接崩。这个坑的价值在于——它逼我去想"聚合查询的结果结构到底该由谁保证"，后来我把兜底逻辑挪到了 SQL 层，用 COALESCE 和 IFNULL 把空值在数据库就处理掉，而不是等 Java 层去 try-catch。

aether-desk（Next.js 全栈知识工作台 Agent）

这个项目我最常被追问的是：RAG 到底是怎么做的？

我的答案是"混合检索 + 引用角标"。纯向量检索在专有名词上表现很差，用户搜"MyBatis-Plus 的 wrapper 用法"，向量相似度会给你一堆"MyBatis 基础教程"。所以我加了关键词检索（BM25 那一路），两路召回之后再做重排，最后把命中片段的原文位置回传给前端，渲染成可以点开的引用角标。

"引用角标"这个设计不是炫技，是解决信任问题。用户看到答案必须能溯源，否则一次幻觉就足以让他再也不打开你的产品。

daily-habit-game（游戏化习惯打卡）

这个项目的卡点是团队分工。三个人写同一个应用，接口对不齐，前端 Mock 数据和后端返回格式对不上，联调那天基本是在吵架。

后来我们先把 OpenAPI 文档定死，用文档生成 Mock，前后端各自对着同一份契约开发。这个经验在面试里比"我实现了打卡功能"值钱得多，因为它讲的是协作。

一个通用的组织方式

我给每个项目固定准备三段话：

  • 一句话说清它是什么（30 秒内讲完，包含技术栈和规模）
  • 一个技术决策及其代价（为什么选 A 不选 B，A 带来了什么新问题）
  • 一个真实的踩坑与修复（发现问题 → 定位 → 解决 → 复盘）

第三段的公式是：现象 → 排查路径 → 根因 → 修复 → 怎么防止再犯。面试官追问时，你不是在被拷问，而是在讲一个自己经历过的事故。

别做的事

  • 不要把没做过的东西写上去。深挖两轮就露馅，而且露馅的代价是整个面试作废。
  • 不要堆技术名词。写了 Kafka 就要准备"为什么不用 RocketMQ"，写了 Redis 就要准备"缓存穿透怎么处理"。
  • 不要只讲成功。讲一个失败的项目并说清你学到了什么，比讲三个完美项目更有说服力。

最后

简历不是履历，是产品说明书。它的目标不是记录你做过什么，而是让面试官在最短时间里找到值得追问的点——而那些点，必须是你准备好的。

## 先说不是什么

现在"Agent"这个词被用得太滥。一个带 system prompt 的 ChatGPT 套壳，也敢叫 Agent。我的划分标准很简单：**它能不能调用外部工具，并根据调用结果决定下一步做什么**。

不能，那是对话机器人；能，才勉强算 Agent。

## 三层递进

**第一层：Prompt**

最原始的形式。你把指令写清楚，模型给你输出。优点是没有工程成本，缺点是没有外部能力——它不知道今天几号，读不了你的文件，改不了你的数据库。

**第二层：Tool Calling（函数调用）**

这是关键的一步。你告诉模型"你有这些工具：查天气、搜数据库、发邮件"，模型在需要的时候不直接回答，而是输出一个结构化的调用请求：`{ "tool": "search", "args": { "q": "..." } }`。

你的代码拿到这个请求，真的去执行，把结果塞回对话，模型再决定继续调用还是给出最终答案。

注意这里的主客体关系：**模型不执行任何东西，它只决定"该调用什么"**。执行权在你手里。这既是 Agent 的能力来源，也是它的安全边界。

**第三层：编排（Orchestration）**

有了工具之后就有了新问题：什么时候该调用？调错了怎么重试？任务太长上下文放不下怎么办？需要人确认怎么办？

这些就是编排层要处理的事，也是各框架差异最大的地方。

## 一个最小循环

抛开框架，Agent 的核心就是一个 while 循环：

```js
const messages = [{ role: 'user', content: '帮我查一下上周的销售数据' }];

while (true) {
  const res = await llm.chat({ messages, tools });

  if (!res.toolCalls) {
    return res.content; // 模型决定直接回答，结束
  }

  for (const call of res.toolCalls) {
    const result = await executeTool(call.name, call.args);
    messages.push({ role: 'tool', name: call.name, content: result });
  }
}
```

就这么点东西。剩下的都是工程细节：怎么防止死循环、怎么限制调用次数、怎么在上下文超长时裁剪、怎么记录每一步便于回放。

## 为什么"真 Tool Calling"值得强调

有些实现是让模型输出一段"看起来像函数调用"的文本，然后用正则去解析。这在 demo 里能跑，生产环境迟早出事——模型加了一句解释、换了引号、输出了 Markdown 代码块，你的正则就崩了。

现在主流模型都支持原生的结构化工具调用（返回 JSON schema 约束的结果），优先用它。可靠性差一个数量级。

## 记忆是个被低估的问题

Agent 跑几轮之后，上下文会迅速膨胀。我最初的做法是把所有历史消息都塞进去，结果第三次调用就开始超时报错，Token 成本也直线上升。

比较合理的分层：

- **短期记忆**：当前会话的上下文，超长时按重要性裁剪（保留系统指令和最近几轮，中间部分做摘要）
- **长期记忆**：跨会话持久化的用户偏好、历史摘要，需要时检索出来注入

这两层要分开存，不要图省事全塞进一个数组。

## 什么时候不该用 Agent

这点很重要，但很少有人讲：

- 任务流程固定、分支可枚举 → 写普通代码，别上 Agent
- 对准确率要求 100%、出错代价极高 → 上 Agent 但必须有人审核环节
- 任务简单到一次 prompt 能解决 → 不要用 Agent 增加不确定性

Agent 的价值在于处理**路径不确定的任务**。如果你的业务流程本来就是确定性的，用 Agent 只是把确定性换成了随机性。

## 小结

理解 Agent 不需要先学框架。把那个 while 循环写出来，手动实现两个工具（比如"查天气"和"搜本地文档"），你会比我讲十分钟的收获更大。

框架解决的是规模问题，理解力解决的是"该不该用"的问题。后者更值钱。

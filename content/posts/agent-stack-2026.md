## 五层栈

看了一圈今年的生产实践，Agent 的技术栈基本收敛成五层了：

**第一层：模型**

选型标准不再是跑分，而是**长任务下的工具调用可靠性**。同一个模型，单轮问答的水平差异不大，但连续调用十次工具、中间还要纠错的能力，差距非常明显。

实用的评估方法是：拿你自己的工具 schema 和真实的多步任务去测，别看公开的榜单。

**第二层：工具与 MCP**

Model Context Protocol 基本赢了连接器这一战——各家都在支持，生态起来了。

但今年大家学到的教训是：**连接器既是攻击面，也是治理面**。作用域受限的 API key、按工作空间划分的连接器白名单、工具调用的审计日志，这些已经从"企业级加分项"变成了基线要求。

**第三层：编排**

市场分成了三种形态：

- 厂商原生平台（云厂商把 Agent 塞进自己的产品线）
- 云上 Agent 运行时（托管执行 + 内置策略）
- **代码优先的编排**（自己写确定性控制流，在决策点调用模型）

有意思的是第三种在严肃的生产部署里占了主导。原因是：Agent 负责判断，代码负责结构。确定性部分交给代码，模型只处理真正需要灵活性的环节，系统的可预测性会好很多。

2024—2025 年那场框架战争，到今年的结论是一句耸肩：**控制流就是代码**。

**第四层：执行环境**

这是今年才独立出来的一层。Agent 要跑代码、要浏览网页，就得有个隔离的地方跑。沙箱化执行变成了可以按需租用的基础设施。

一句话原则：只要你的 Agent 会执行代码或访问网络，隔离执行就不是可选项。

**第五层：护栏与评估**

区分 demo 和生产的一层。

现在的标准已经从"输入输出过滤"升级到**动作级别的筛查**——每个 Agent 动作都要评估是否存在提示注入、有害内容、敏感数据外泄。

配套的是：真实任务分布上的回归评估集、有明确负责人的抽样人工复核、按用例的紧急开关。建议把运行成本的 10%—20% 预算放在这一层。

## 搭建顺序：从第五层往上

给新团队的建议很反直觉：**先做评估，再选模型，再接少量工具，再写编排，最后才上沙箱**。

从顶层（编排器）开始建的团队，交付的是 demo；从底层（评估）开始建的团队，交付的是系统。

## 单智能体 vs 多智能体

这是今年最有争议的话题，数据也最打脸。

有研究给出的结论是：在给相同工具和上下文的情况下，**单个 Agent 在 64% 的基准任务上达到或超过了多智能体系统**，而多智能体平均只带来约 2.1 个百分点的准确率提升，成本却接近翻倍。

原因不难理解。多智能体的协调是有税金的：任务要拆解、结果要同步、上下文要传递、冲突要仲裁。另一组数据说，辩论式多智能体的成本约为单次模型调用的 2.5 倍。

所以现在的共识打法是：**先用单智能体，直到你看到一个清晰的边界——某个子任务确实不该由同一个 Agent 跨越**，再拆。

该拆的典型场景：跨域的复杂工作（比如一个任务需要同时写代码、查法务条款、做数据分析，且三者的上下文几乎不重叠）。

## 还有一条主线：记忆

长期记忆正在成为 Agent 的差异化能力，而且已经超出了"向量库存历史"的范畴。分类在硬化：

- **语义记忆**：知道什么（事实、偏好）
- **情景记忆**：发生过什么（事件、轨迹）
- **程序性记忆**：怎么做（流程、技能）

今年一篇被反复引用的观点是：Agent 变聪明不是靠存得更多，而是靠**把存的东西整理压缩**。

对应到工程上，checkpointer（单会话）和 memory store（跨会话）要分开设计，同时"记忆卫生"——该忘什么、什么时候压缩、怎么防止上下文污染——跟存储层本身一样重要。

## 我的收获

作为一个还在学校的开发者，这一年的信息密度大得有点窒息。但理清之后反而踏实了：框架会一直换，这五层不会；模型会一直升级，评估、沙箱、护栏这三件事不会过时。

把时间花在不容易过期的东西上，是我在 2026 年最确定的一个判断。

## 为什么要做这个

起因很朴素：我自己的笔记、PDF、项目文档散在好几个地方，想问一句"上次那个 MyBatis 的坑是怎么修的"，得手动翻半天。

现成工具不是不好，但有两个问题：一是文档要上传到别人服务器，二是它们给的答案不能溯源。于是决定自己写一个放本地的。

技术选型是 Next.js 全栈，一个仓库搞定前端、API 和数据层，对个人项目来说省掉了一半的部署成本。

## 决策一：会话持久化必须自己做

第一版我把对话存在内存里，刷新页面就没了。这在使用上完全不可接受——你跟一个知识工具的对话是长期资产，不是一次性的聊天。

改成数据库持久化之后，顺带解决了另一个问题：**历史会话本身成了检索源**。用户问过一个问题的上下文，在两周后问相关问题时能被调用出来。这一步是后来加的，效果比预想的好。

实现上的注意点：消息表要存角色、工具调用记录、token 消耗和引用来源，别只存文本内容。没有这些元数据，后面做分析和优化就抓瞎了。

## 决策二：真 Tool Calling，不用正则解析

我给 Agent 挂的工具不多：检索本地知识库、读指定文档、做关键词搜索、生成待办。

这里踩过一个坑：最初我让模型输出 `TOOL: xxx ARGS: xxx` 这样的文本格式，自己写正则解析。跑通了大概七成的情况，剩下的三成里模型会加解释、会加 Markdown 格式、会改参数顺序。

换成模型原生的结构化工具调用之后，成功率直接拉满。结论很明确：**不要跟模型的输出格式做约定，用 schema 约束它**。

## 决策三：混合 RAG，而不是纯向量

纯向量检索在我自己的文档上表现很差。搜"Wrapper 构造器的用法"，返回的是一堆"MyBatis 入门教程"。语义相近，但答非所问。

我的方案是关键词检索和向量检索并行召回，然后做一轮重排。关键词那路负责专有名词和精确匹配，向量那路负责语义相近，重排模型再统一打分。

代价是复杂度上升——两套索引、一次重排、更多的调参空间。但这是这个产品唯一不能妥协的地方，检索质量不行，后面全白搭。

## 决策四：引用角标是信任的地基

每个回答里用到的片段，我都在前端渲染成可以点开的小角标，点开能看到原文出处和具体段落。

这个功能花了不少时间，但它解决的是 AI 产品最核心的问题：**用户凭什么信你**。

有角标，用户会自己去验证，验证几次对了之后他就敢用；没角标，一次幻觉就足够让他彻底放弃。我做产品的时间不长，但这一条是我目前最确定的判断。

## 决策五：人在环（HITL）不是可选项

Agent 想执行"有副作用"的操作——比如修改数据库、发通知、删除文件——必须先停下拉起一个待用户确认的卡片，用户点确认才继续。

实现上就是在工具定义里加一个 `requiresApproval` 标记，执行前拦截，把待办写进队列，等前端回调。

加上这一层之后，我自己用起来反而更敢让它动手了。这跟现实中的授权逻辑是一样的：有审批流程，才敢放权。

## 决策六：Generative UI

最后一个有意思的点：让 Agent 直接输出结构化的 UI 描述，前端渲染成对应的组件——比如检索结果渲染成可展开的卡片列表，待办渲染成带 checkbox 的清单，而不是一坨 Markdown 文本。

这比纯文本输出的体验好很多，但要注意约束：必须限定组件白名单和字段 schema，否则模型输出的 JSON 千奇百怪，前端直接白屏。

## 还没解决的问题

诚实地说几个没做好的：

- 长文档的分块策略还是太粗糙，按固定长度切会切断语义
- 没有像样的评估集，"感觉变好了"和"真的变好了"之间缺少证据
- Token 成本没有精细管控，长会话一次能烧掉不少

第二点我打算优先补。没有 eval 的 Agent 优化，本质上是在碰运气。

## 小结

这个项目最大的收获不是学会了某个框架，而是建立了一种判断力：**哪些环节必须可靠（检索、引用、审批），哪些环节可以先用笨办法（分块、摘要）**。

资源有限的时候，这个判断比技术选型重要得多。
